## Description

**Outcome:** The embedded creative agent can inspect every storyboard source photo without placing the project's original uploads into one oversized MCP response. It receives a numbered whole-storyboard contact sheet first, then bounded 640px preview pages, and is instructed to synthesize one coherent creative assessment only after every page is read.

**Why this matters:** High-resolution photo collections could exceed native vision-provider attachment capacity. Paging alone could also bias a recommendation toward the final batch; the overview preserves the collection's visual continuity before individual details are examined.

**Runtime/user impact:** `read_storyboard_photos` now accepts an optional `offset`. Offset zero returns the overview plus up to six detail images; later offsets return up to six details and `nextOffset` indicates whether more photos remain.

## Scope and Boundaries

**In scope**

- Preview-backed MCP paging with a fixed page size of six.
- A five-column, numbered JPEG contact sheet for the first page.
- Session guidance requiring overview → all pages → one reconciled assessment.
- In-memory preview recovery for legacy photos missing their stored derivative.

**Out of scope**

- Database, REST API, object-storage schema, or normal project photo-analysis changes.
- Persistent AI observations, automatic creative-field writes, and provider/model changes.

**Must remain true**

- The tool remains read-only and project-scoped.
- A missing source object is reported with its photo ID; it is never silently omitted.
- Stored previews are returned in preference to original bytes.

## Changes Made

- Added `createPhotoContactSheet`, which renders contained 200×150px image cells in five columns with manifest-matching numeric labels.
- Extended `read_storyboard_photos` with `offset`, `totalPhotoCount`, `returnedPhotoCount`, `nextOffset`, `overviewIncluded`, and per-photo `globalIndex` metadata.
- Switched detailed MCP image blocks to the upload-time 640px JPEG preview. If that derivative is absent, the tool generates a 640px preview in memory from one original at a time.
- Updated native session and per-turn instructions to prevent a recommendation or proposal before `nextOffset` is `null`.
- Added tests for the contact sheet layout, preview preference, seven-photo paging, missing-preview recovery, missing-source failures, and the new agent guidance.

## Decisions and Tradeoffs

### Decision: Whole-collection overview plus bounded detail pages

- **Decision:** Return a contact sheet once at offset zero and no more than six 640px preview images per tool call.
- **Constraint:** Native agent runtimes can reject a single response containing many original uploads.
- **Gain:** The agent sees global palette, chronology, recurring subjects, and motifs before detail analysis, while each response stays bounded.
- **Give up:** Fine detail in the overview is intentionally limited; the matching detail pages provide that inspection.
- **Rejected alternative:** Detail pages without an overview reduce response size but do not provide an explicit global visual anchor.
- **Reversal cost:** Replacing this shape requires an MCP contract and agent-guidance update, but no migration.
- **Unconfirmed assumption:** A credentialed native provider session will follow the pagination instruction in real browser use; the MCP contract and guidance are covered by automated tests.

## Risks, Rollout, and Rollback

- **Known risk:** A native provider could stop before it follows `nextOffset` in a real interactive session.
- **Mitigation:** The contact sheet provides complete collection context immediately; explicit session guidance requires every page before a recommendation.
- **Rollout:** Takes effect when the API process runs this revision. Existing projects need no migration because preview keys are deterministic; missing legacy previews fall back in memory.
- **Rollback:** Revert commit `833b2a0` to restore the prior MCP response behavior.
- **Breaking changes:** None for REST clients or stored project data. MCP callers should follow `nextOffset` to inspect every photo.
